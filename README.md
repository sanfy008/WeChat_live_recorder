# 微信直播录音转录

电脑端采集微信直播的声音 → 实时转写成文字 → 输出结构化数据供 LLM 分析。

**核心思路：不碰微信。** 直接从声卡输出端录声音（WASAPI loopback），
不装证书、不改代理、不担心微信版本更新导致失效。

---

## 快速开始

```bash
# 1. 环境准备（只需一次）
uv venv .venv --python 3.12
.venv/Scripts/python.exe -m ensurepip
.venv/Scripts/python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 2. 自检
.venv/Scripts/python.exe -m wxlive doctor

# 3. 开始录制（一直录到 Ctrl+C）
.venv/Scripts/python.exe -m wxlive record

# 4. 录 60 分钟
.venv/Scripts/python.exe -m wxlive record --minutes 60 --name 某场直播
```

> 远程/低配机器建议直接用精简环境 `.venv-trim`（316MB，启动脚本已优先用它），
> 见下文「环境精简」。

产物在 `output/recordings/`：

| 文件 | 用途 |
|---|---|
| `<会话>.wav` | 原始音频，**不要删**。ASR 模型会升级，原始音频不会贬值 |
| `<会话>.md` | 人读逐字稿，**段落聚合**（见「输出结构」） |
| `<会话>.json` | 结构化数据，喂给 LLM 用，逐句带时间戳 |
| `<会话>.jsonl` | 逐句追加，崩溃也不丢 |

## 图形界面（推荐）

双击 **`启动.bat`** 即可，不需要命令行。

需要看报错时用 `启动-调试.bat`（会保留控制台窗口）。

### 五个页签

| 页签 | 用途 |
|---|---|
| **录制** | 选设备、定时长、开实时转写、静音自动停；下方实时显示转写内容 |
| **视频号下载** | 抓流工具捕获到的回放列表 → 一键解密下载音频（详见下节） |
| **转写与整理** | 选音频 → 选模型 → 三步后处理 → 结果预览 |
| **设置** | API 接入、默认模型、切分参数、领域词表，改完自动保存 |
| **运行日志** | 所有操作和错误的时间戳记录 |

### 界面里能配什么

**① API 接入**
- 网关地址（默认 `http://127.0.0.1:3425/v1`，也可填官方 OpenAI 兼容地址）
- API Key（带显示/隐藏切换）
- 「测试连接并拉取模型」—— 实测能从 magpie 拉到 **41 个模型**，自动填进下拉框

**② 模型选择**（两级，都可下拉选）
- **转写模型**：Gemini 系列（自动发现）+ 本地 Whisper，标注了各自的实测特点
- **整理模型**：DeepSeek / Claude / GPT 等，用于纠错和生成要点
- 单次音频上限、是否启用领域词表

**③ 音频与切分**
- 片段最长秒数、静音判定秒数、云端最小块秒数，每项旁边都有说明为什么这么设

**④ 领域词表**
- 可指定任意 JSON 词表路径，或一键用默认

### 三步后处理（可独立开关）

| 步骤 | 作用 | 建议 |
|---|---|---|
| ① 同音字纠错 | 用 LLM 拿领域词表再校对一遍 | **强烈建议开** |
| ② 暗语展开 | `白省` → `白省（白云省实）` | 建议开，方便检索 |
| ③ 生成要点 | 输出话题 / 学校评价 / 建议 / 存疑点 | 长回放建议开 |

### 配置存在哪

`config/user.json`，只覆盖你改过的字段，升级代码不会冲掉。

点「恢复默认」可一键清空。

## 视频号下载（回放专用）

比声卡回环音质更好、CPU 几乎为零，适合**已经把回放放完**、想要干净音轨的场景。

### 前置：抓流工具要跑起来

```bash
cd tools/wxcd
./wx_video_download.exe        # 根命令启动，不要加 server 子命令
```

工具会把系统代理改成 `127.0.0.1:2023`（它自己的 MITM 端口），
所以**必须在微信里真的播一下目标回放**，让它捕获到地址和解密密钥。

### 用法

GUI「视频号下载」页 → 「刷新列表」→ 选中 → 「下载选中项的音频」。

功能点：

| 能力 | 说明 |
|---|---|
| **搜索** | 交给工具服务端过滤（`keyword`），输入停 400ms 防抖 |
| **翻页** | 每页 20/50/100/200 可选，显示「第 N / M 页」 |
| **解析选中** | HEAD 探测：地址是否过期、要不要解密、文件多大（如「加密 / 621.2 MB」）|
| **删除选中 / 清空列表** | **只隐藏本工具列表**，随时可「恢复被删除的」 |
| **已下载标记** | 下过的显示「已下载 N 分钟」，可勾「只看未下载的」过滤 |
| **中止** | 不硬杀线程，下完当前这条再停 |

### 两个必须知道的点

**1. 删除是"本侧隐藏"，不是真删。** 抓流工具的内容 API 只有
`list / detail / relations`，没有 delete/clear（核对过它的 `routes.go`）。
去改它的 `data.db` 风险太大——WAL 模式且运行中，写坏会丢全部捕获记录，
而那些记录是"地址过期后重新取址"的唯一凭据。

**2. 系统代理会一直停在不正常的地方。** 工具关掉后代理**仍指向 2023**，
2023 没人监听 → 所有走系统代理的应用（浏览器、微信）全部断网。
下载页顶部有常驻状态条每 60 秒自检，异常时变橙色，点「还原系统代理」即回 10808。

> 细节与调研（对比 3 个 GitHub 同类项目）见 [下载器GUI改进调研](docs/下载器GUI改进调研.md)。

## 长回放怎么处理

130 分钟回放不需要边播边转：

```bash
# 1. 先纯录音（CPU 占用极低，最稳）
python record_only.py --minutes 132 --name 回放标题 --silence-stop 40

# 2. 录完再批量转
python -m wxlive transcribe output/recordings/xxx.wav
```

GUI 里对应：「录制」页 **取消勾选「录制同时实时转写」**，勾上「静音自动停止」。

**实测结论：2 倍速播放不影响转写质量。**
用 Gemini 转写 2 倍速音频，`16南`、`白六`、`白省`、`BS`、`小金`、`白云区铁一` 全部识别正确。
播放器 2 倍速是保持音高的时间压缩，ASR 完全能吃。**130 分钟可以压到 65 分钟。**
不要做「降速还原」——实测降速反而更差（音调被压低）。

## 转写引擎怎么选

支持三种引擎，实测数据见 [ASR方案对比实测](docs/ASR方案对比实测.md)。

| 引擎 | 中文准确率 | 180s 音频耗时 | 说明 |
|---|---|---|---|
| **Gemini 4-argon** | **最高** | 20s（RTF 0.11） | 校名/术语最准，推荐 |
| Gemini 4-hydrogen | 高 | 8s（RTF 0.07） | 最快，偶有漏字 |
| Gemini 3.8-flash | 高 | 9s | 会输出繁体（已自动转简） |
| whisper small（本地） | 中 | 72s（RTF 0.41） | 同音字错多，但永不失效 |
| whisper medium（本地） | 中+ | 300s（RTF 1.75） | 慢 4 倍，性价比差 |

```bash
--engine auto      # 默认：Gemini 优先，失败自动降级本地
--engine local     # 纯本地，隐私安全，不依赖网络
--engine gemini    # 纯云端（仍保留本地兜底，防止中断）
```

**实测质量差异**（同一段真实直播音频）：

| 原意 | whisper small | Gemini |
|---|---|---|
| 寒假冬令营 | 它行驾…东丽银 ❌ | ✅ 他寒假会有一个冬令营 |
| 民办 / 公办 | 明半 / 公半 ❌ | ✅ 民办 / 公办 |
| 省实（校名） | 省市用品 ❌ | ⚠️ 省实用品（部分对） |
| 730+ / 670+ | 730家 / 670家 ❌ | ✅ 730+ / 670+ |
| 指标到校 | 抗礼 ❌ | ✅ 指标到校 |

**为什么默认 auto 而不是纯云端**：Gemini 有单次 120 秒上限和内容安全过滤
（实测 180s 音频被 `content_filter` 拒绝），长直播必然中途断。
auto 模式下连续失败 3 次即整场降级本地，保证录音链路不中断。

**关于 DeepSeek**：不能听音频（实测回复"无法接收音频"）。但它可以做事后
同音字纠错，效果不错且成本极低（120s 音频约 $0.000065），详见实测报告。

## 领域词表（XSC 暗语）

广州小升初直播里全是暗语：「白省」=白云省实、「鸡腿」=铁一、「芝麻鸡」=六中、
「JGF」=金广附。ASR 模型不认识这些词，必然听错。词表解决三件事：

1. **注入 ASR prompt** —— 让模型知道这些词存在（Gemini 和本地 whisper 都生效）
2. **转写后错字纠正** —— 按实测错误表替换（`省市用品`→`省实`、`MKY区`→`MK外区`）
3. **输出时展开暗语** —— 写成 `白省（白云省实）`，保留原文可追溯，方便检索

```bash
--no-lexicon            # 关闭词表（默认开启）
--lexicon-path my.json  # 用自定义词表
```

### 自己维护词表

编辑 `lexicon/xsc.json`，改完下次运行自动生效（与内置表合并，不会覆盖）：

```json
{
  "schools": ["你的学校名"],
  "terms": ["你的术语"],
  "codes": {"新暗语": "正式名"},
  "corrections": {"ASR听错的样子": "正确写法"}
}
```

**维护建议**：每场直播后，把 md 里读不通的地方对一下录音，
把「听错的样子」加进 `corrections`。跑两三场之后，准确率会明显稳定。

### 暗语解码规则（来自资料整理）

| 类型 | 例子 |
|---|---|
| 拼音首字母 | SS=省实、HF=华附、JGF=金广附、TX=天省 |
| 谐音联想 | 浴室=育才实验、金店/周大福=中大附、二叔=二中苏元 |
| 食物关联 | 鸡腿=铁一、烧鸡=白云华赋、芝麻鸡=六中、黄焖鸡=黄埔铁英 |
| 地点关联 | 农讲所=省实、流花湖=广雅、区庄=执信、天河客运站=天省 |
| 学校历史 | 张之洞/张府=广雅 |

词表已内置上述常见项，以及实测直播中补充的「白省」「白雅」「白六」「龙涛」「培文」等。

## 输出结构

`<会话>.json` 关键字段：

```json
{
  "source": "wechat_channels",
  "session_id": "20261116_200000_某场直播",
  "started_at": "2026-11-16T20:00:00",
  "duration_seconds": 3600.0,
  "audio_file": "20261116_200000_某场直播.wav",
  "segments": [
    {"start": 12.4, "end": 18.9, "text": "...", "speaker": null}
  ],
  "full_text": "...",
  "meta": {"asr": {"audio_seconds": 3600, "rtf": 0.41}}
}
```

`speaker` 字段预留了说话人分离的位置，当前为 `null`。
带秒级 `start/end` 是为了让 LLM 能做「谁在什么时候说了什么」的溯源式分析 ——
只给一整段大文本，LLM 只能做泛泛总结。

### md 是段落聚合的，不是逐句

**秒级时间戳是伪精度。** Gemini 不返回逐句时间戳，我们按字数比例估算，
误差可达 ±10~30 秒——看着细，其实对不上真实位置。而实测 81 分钟那条转录里，
时间戳占文本量 **35.2%**（正文 23850 字 / 时间戳 12945 字），
喂给 LLM 时三分之一 token 花在不准确的秒数上。

所以 `.md` 改成语义聚合：优先在主播的转折话术处断段
（「有家长问…」「下一个问题」「来我们看」「那接下来」），
没有转折信号才用 60 秒 / 400 字兜底。时间戳开销 **35.2% → 5.1%**。

`.json` / `.jsonl` **保持逐句 + 原始时间戳不变**——将来要精确回查或接说话人分离时用得上。
实现见 `wxlive/render.py`，细节见 [输出格式优化](docs/输出格式优化.md)。

## 设计要点

### 为什么用 WASAPI loopback 而不是抓流

抓 FLV 直播流（mitmproxy + JSBridge 注入）音质更好，但要装根证书、
要跟微信页面结构对抗、随时可能因改版失效。
loopback 从声卡输出端录，与播放器解耦，任何声音都能录 —— 包括微信直播、
群语音、视频通话。代价是必须有声音真的在放（静音则录不到）。

### 线程模型

```
主线程：采集队列 → 重采样 → VAD 切分 → 投递转写队列
转写线程：转写队列 → ASR → 写盘
```

必须分离。ASR 在 CPU 上 RTF 可能 >1，串在主线程会让采集队列灌满、回调整块丢帧 ——
一旦丢帧，录音链路就废了。分离后录音永不阻塞，转写慢只是排队。

### 踩过的坑（都已修复并有回归测试）

| 问题 | 症状 | 修复 |
|---|---|---|
| **未重采样** | 48k 音频当 16k 喂给 whisper，相当于慢放 3 倍，输出**全是幻觉**且不报错 | `resample.py` + `Transcriber` 入口强制转换 |
| **VAD 校准期误判** | 开头 3 秒阈值还是初始值，整段被判"有声"，粘成巨型片段 → 丢句 | 校准期只采样不判定，攒下的音频校准后补处理 |
| **阈值被上限压死** | 高底噪环境阈值 0.05 < 底噪 0.059 → 全部判"有声" → 永不切句 | 阈值必须 ≥ 底噪×1.2，上限不再压穿底线 |
| **energy VAD 遇 BGM 失效** | 直播间有持续背景音乐，找不到静音间隙 | `max_segment` 兜底粗切 + whisper 内置 Silero VAD 精切 |
| **initial_prompt 污染** | prompt 被当"上文"，模型复读 prompt 内容 | 默认置空 |
| **whisper 重复循环** | 长音频反复吐同一句 | `_collapse_repeats()` 压制，且不误伤口语重复 |
| **GBK 控制台崩溃** | 打印 emoji/中文抛 `UnicodeEncodeError` | `wxlive/__init__.py` 统一 force UTF-8 |

### 性能取舍（实测，别凭直觉优化）

| 想法 | 实测结论 |
|---|---|
| 把音频压成 2 倍速再传，省 token | **否定**。这里只能做 `soxr` 变速变调（不是播放器的保音高压缩），音高被压低，识别负担反增，实测 0.34x~1.56x 乱跳 |
| 并发转写 | **有效**。网关能吃 2-3 并发，整体 **2.4-2.6x** |
| 转写前剔除静音段 | **几乎无收益**（<1%）。直播里主播基本一直在说，静音段极少；且误切"念评论"的风险不可接受 |

详见 [性能优化实测](docs/性能优化实测.md)。

### 验证采集链路时，别把"没播放"误判成"录不到"

排查"录不到声音"时，**播放这一端必须是同步且确定的**。
实测踩坑：用 `Start-Process <wav>` 播测试音，它对 WAV 走了默认关联程序但**没真发声**，
录到 RMS=0，差点误判成采集代码有 bug。改用 `.NET SoundPlayer.PlaySync()`（退出码 0）后
立刻录到峰值 0.2500（正好等于设定振幅）。

**可复用的验证方法**：播一段已知振幅的正弦波，比对采集到的峰值。
峰值精确吻合 = 增益/通道/采样率全对，这是比"看代码"强得多的证据。

## 已知限制

1. **必须有声音在放**：静音 / 系统独占音频时录不到。
2. **采样的是"混音"**：如果同时有别的程序在放声音（微信消息提示音、其他视频），
   会一起被录进去。这是 loopback 的固有特性，不是 bug。
3. **不做说话人分离**：`speaker` 字段是预留位。需要的话可接 `pyannote.audio`，
   但 CPU 上很慢，建议离线跑。
4. **UU 远程虚拟声卡**：本机因装了 UU 远程，系统**唯一注册的音频端点**就是它
   （Realtek / Intel 显示音频都没有端点，蓝牙耳机虽已配对但端点 `Present=False`）。
   实测能正常录到系统声音，无需处理。若哪天录不到，先跑 `doctor` 看设备。

5. **静音 ≠ 采集坏了**：同一条端点实测过 RMS 从 0.096 一路降到 0.00000
   （直播中途停止播放）。录到静音时先确认对端是否真的在出声，
   再看 WAV 体积——16k mono 正常约 **1.83 MB/分钟**，远小于此才是真没录到。

## 音源方式：两种可选

GUI「录制」页顶部可切换，各有适用场景。

| | 声卡回环（默认） | 流地址直录 |
|---|---|---|
| 配置 | **零配置**，开箱可用 | 需先拿到流地址 |
| 音质 | 经声卡重编码 | **原始音轨** |
| CPU | 低 | **几乎为零** |
| 需播放 | 必须 | 不需要，可静音录 |
| 受其他程序干扰 | 会 | 不会 |
| 长时间无人值守 | 需保持播放 | 可 |

**流地址直录用法**：

```bash
python -m wxlive stream "https://xxx.flv" --name 某场直播
```

或在 GUI 里：选「流地址直录」→ 填地址 → 点「测试」确认能拉 → 开始录制。

特性：先探测有无音轨再录、断流自动重连、90 秒无数据判定断流、直接输出 16k 单声道省一半磁盘。

**注意**：微信视频号不公开流地址，需用抓包工具获取（带签名的 flv/m3u8，有时效）。
拿不到就用声卡回环，零配置也能用。详见 [流地址录制方案](docs/流地址录制方案.md)。
