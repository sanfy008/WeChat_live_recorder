# ASR 输出质量治理：幻觉拦截、分句修复、时间戳诚信

> 2026-11-16 17:45–18:20 实测与实现记录
> 触发点：时间戳该给到多细？逆推代码时撞上两个更严重的真问题

---

## 一、先纠正一个前提：时间戳不是发给 LLM 时该改的

最初的假设是"既然最后要把时间戳改掉，不如在 ASR prompt 里明确不要"。

**这个位置是错的。** 逆推代码链路，时间戳有三个独立决策点：

| 层 | 位置 | 改动前的实际状态 | 谁加的 |
|---|---|---|---|
| ① ASR prompt | `gemini_asr.py` PROMPT | **本来就没有要求时间戳** | 无（无辜） |
| ② 内部生成 | `gemini_asr.py` 句级分配 | `span = dur * len/total` **按字数硬摊** | 我们 |
| ③ 喂分析 LLM | `postprocess.py` `build_digest` | **逐句带时间戳** | 我们 |

模型只吐纯文本行，时间戳从头到尾是我们自己编上去的。
所以在 ① 加"不要时间戳"收益为零——那正是本轮**没有**做的事。

## 二、伪精度到底有多假：用 whisper 真实对齐测出来了

取 `广州x升初鸡头凤尾如何选.wav` 的 1200–1310s（110 秒块，24 句），
用 faster-whisper small 拿真实时间戳做基准逐句对比：

| # | 我们（按字数均摊） | whisper（真实） | 偏差 |
|---|---|---|---|
| 0 | 0.0s | 0.0s | 0.0s |
| 5 | 13.0s | 14.7s | 1.7s |
| 7 | 24.4s | 19.2s | 5.2s |
| 9 | 33.2s | 22.9s | **10.3s** |
| 11 | 46.2s | 27.5s | **18.7s** |

**块内起点绝对偏差：中位 19.3s，平均 23.9s，最大 59.0s。**
110 秒的块，中位误差占块长 18%。

结论：`[00:02:34]` 不是"精度够不够"的问题，是**往精确的格式里填不可靠的数值**。

## 三、真实数据里的账

同一条 81 分钟转录（863 句，23850 字）：

| 形态 | 时间戳字符 | 占比 |
|---|---|---|
| 逐句 md | 12,945 | **35.2%** |
| 段落聚合 md | ~1,900 | **5.1%** |

喂 `build_digest` 的输入（改前 vs 改后）：

| 口径 | 字符数 | 是否触发 30000 分块 |
|---|---|---|
| 逐句 + 句级时间戳 | 34,205 | **是** |
| 段落聚合 + 段级时间 | 26,065 | 否 |
| 降幅 | **23.8%** | — |

**关键不只是省 token**：触发分块意味着全片被切成几段分别摘要再归并，
**全局视野丢失**，这是实打实的质量损失。内容零丢失已验证（23850 字逐字一致）。

## 四、撞上的真问题 ①：模型幻觉进了正文

### 现象

`20261116_170553_广州x升初鸡头凤尾如何选.json` 里：

```
[1310-1420] 抱歉，我无法访问或接收您提到的音频文件 `[attachment audio/wav]`，
            当前对话中未包含实际音频内容…
[2020-2100] 未收到有效的音频文件，仅有 `[attachment audio/wav]` 占位文本，
            无法进行转写…
```

`20261116_172957_越秀区各个业主怎么进.json` 里还有 4 条。

### 四条实测证据

**1. 音频是好的。** 抽那 5 个位置读原始 WAV：RMS 0.093–0.117，峰值 0.96，
**比正常对照区（RMS 0.086）还响**。不是录音中断，不是静音。

**2. 100% 落在 110 秒切片边界上。** 起点在 300s 块内偏移全是 0 / 110 / 220，
即切片块起点或尾部残余块。切片把音频硬切断，模型拿到边界块后拒绝转写。

**3. 代码认为全部成功。** meta 写着 `primary_fail: 0, degraded: false`——
HTTP 返回 200 就算成功，幻觉句一路进了 json / md / jsonl / 纠错 / 摘要。

**4. 时有时无。** 同一份 WAV 跑两次：15:29 的产物 0 条，17:05 的产物 5 条
（句数也差 9.6%）。是模型对边界块的不稳定行为，不是确定性故障。

> 第 4 点决定了修法：**既然是瞬时的，重试就有效。**
> 实测同一个幻觉块原样连跑 3 次全部正常，错开 ±5s 也能正常出内容。

### 修法：检测 + 重试 + 三分/二分 + 整块占位

新增 `wxlive/quality.py`，判定原则是**宁可漏判，不可误杀**——
误杀会丢掉主播真实说过的话，比漏判更糟。

恢复梯度（`gemini_asr._transcribe_piece`）：

1. **原样重试 1 次** — 对付瞬时抖动，成本最低
2. **三分重切**（仅 depth0 且 ≥45s）— 把**两个**边界都挪进块内。
   这一步是实测逼出来的：只二分会让子块跌破门槛而放弃
3. **二分**（depth<3 且 ≥12s）— 继续挪边界
4. **整块落占位** — 抛 `_PieceFailed` 到最外层，按整块写**一个**占位

第 4 步的设计有实测依据：如果让每个碎片各落一个占位，
"1 个 110 秒缺口"会变成"7 个 15 秒占位"，读者无法判断缺口有多大。

**长度异常（输出过短）只重试、不二分。**
理由：短可能本来就是真实情况（这块真没说话），二分只会让碎片更碎、
反而更容易触发幻觉。实测这条约束把误切次数从 22 次降到 3 次。

## 五、撞上的真问题 ②：整块塌成一句（比幻觉更普遍）

统计 7 份真实产物，**每一份都有** 1~10 处"单句横跨 110 秒"：

| 产物 | 句数 | 跨 >60s 的"句子" |
|---|---|---|
| 130min 回放 | 1561 | 5 |
| xiaolin_xsc_6 | 1956 | 3 |
| 鸡头凤尾 15:29 | 955 | 1 |
| 越秀 15:40 | 1733 | 1 |
| 小升初跨区 | 1759 | **10** |
| 鸡头凤尾 17:05 | 863 | 7 |
| 越秀 17:29 | 2020 | 5 |

这类行**内容是真的**，只是模型没分句。危害在于：
一句横跨 110 秒在物理上不可能，句级时间戳全废，
而且它突破了段落聚合的 `max_seconds` 兜底，污染"段级时间可信"这个前提。

修法在 `_finalize()`：内容没问题但 `looks_unsplit()` 判定塌陷 →
重试一次 → 仍塌陷就 `split_long_line()` 按标点硬拆（兜底，至少让时间分配不完全失效）。

## 六、修法中途发现的真 bug：正常音频被判失败

第一版二分门槛是 40 秒。真实录音验证发现 1540s 处两段共 56 秒被落占位。
回查原始音频：**RMS 0.132、峰值 0.70、内容完全正常**
（"有的学生过了K，有的学生过了KP甚至F…"）。

根因：二分到 28 秒碎片后跌破 40 秒门槛 → 直接放弃。
修法：门槛降到 12 秒 + 增加三分步骤，让子块重新获得可再分的长度余量。
修复后同样 30 分钟音频的失败块从 **2 块降到 0 块**。

> 这个 bug 说明一件事：**合成/静音音频测不出这类问题。**
> 必须拿真实直播录音跑，才会暴露"判据过严把正常内容丢了"。

## 七、到底改了什么

### 新增文件

| 文件 | 作用 |
|---|---|
| `wxlive/quality.py` | 幻觉判定 / 长度异常 / 分句塌陷判定 / 标点硬拆 / 占位文案 |

### 修改文件

| 文件 | 改动 |
|---|---|
| `wxlive/gemini_asr.py` | 重试 + 三分/二分恢复 + `_PieceFailed` 整块占位 + 质量统计入 stats；PROMPT 加第 6/7 条（明确"不输出时间戳/序号/说话人标签"）；句级时间戳标 `ts_source="estimated"` |
| `wxlive/postprocess.py` | `build_digest` 改用段落聚合喂 LLM（不再逐句喂时间戳）；新增 `_span()` |
| `wxlive/session.py` | `ts_source` 字段透传落 json + jsonl |

### meta 现在会如实报账

改动前只有 `primary_ok / primary_fail / degraded`——幻觉翻倍也看不出来。
现在多了：

```json
"bad_detected": 3,        // 检出幻觉/长度异常次数
"unsplit_detected": 3,    // 分句失败次数
"recovered": 2,           // 重试/切分救回次数
"failed_chunks": [],      // 真丢了内容的区间（落占位）
"suspect_chunks": []      // 短得可疑但照实保留
```

`failed_chunks` 和 `suspect_chunks` 分开记，才能区分"确实有缺口"和"这块内容本来就少"。

## 十、没做的事，和为什么

| 未做 | 理由 |
|---|---|
| 在 ASR prompt 里加"不要时间戳" | 模型本来就不输出，加了只增加 prompt 长度和幻觉概率 |
| 现在就上 diarization | 模型不准则误切，反而损害质量。而且幻觉还没清完，先修地基 |
| 丢弃句级时间戳 | 将来接 diarization / 精确回查要用。保留但标 `estimated`，不让它冒充精确 |

**零成本替代 diarization** 的想法（还没实现）：`render.py` 的转折话术已能识别
"有家长问 XXX"。可以把这类段渲染成 Markdown 引用块，视觉上就是按发言轮次，
问答关系一目了然，成本为零。

## 十一、一次方法论层面的教训

这轮最值得记的不是改了哪些代码，而是**验证方式的选择**：

第一版逻辑用"合成音频 + 桩函数"测试，全部通过。
但真实录音一跑就暴露出"正常音频被判失败、丢掉 56 秒真实内容"。

**桩函数能验证"代码按我设想的分支走"，验证不了"判据本身对不对"。**
判据的松紧只能拿真实数据校准——这也是为什么这一轮的每个数字都来自
真实产物或真实 WAV，而不是构造出来的样例。
