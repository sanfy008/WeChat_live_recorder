> 主线：GUI 直播推送 → NAS 录制 → 转写，整条链路首次真机跑通

## 一、这一轮最该记住的结论

**我连续三次以为"已经部署好了"，三次都是假象。**

| 时间 | 我以为 | 实际 |
|---|---|---|
| 18:13 | scp 了 `livesilence.py` / `nas_runner.py`，重启服务，静音修复生效 | ✅ 这次是真的（代码在宿主机目录、且服务跑在宿主机） |
| 20:32 | `pkill` 后 PID 变了 = 新代码已加载 | ⚠️ PID 变了是容器自己重启，**代码根本没换** |
| 20:50 | 重建镜像后 `_force_ipv4_url` 计数=3 = 部署成功 | ✅ 这次是真的 |

真正的原因：

```
容器挂载只有两个：
  ./data       → /app/data
  ./hf_cache   → /app/hf_cache

代码 /app/wxlive 是 COPY 进镜像的 —— 不是挂载
```

所以对 `/vol1/1000/docker/wxlive-nas/wxlive/` 做的 `scp`，**对运行中的服务毫无影响**。
要从头重建镜像（`docker compose up -d --build`）才会生效。

### 判据修正

| 错误判据 | 正确判据 |
|---|---|
| `pkill` 后 PID 变了 → 部署成功 | `docker exec <容器> grep -c <新标记> /app/<文件>` |
| 文件 mtime 比进程启动时间新 → 已加载 | 容器**内部**的文件内容 |
| 代码传上去了 | 镜像是重建过的（`docker images` 的 CREATED） |

**这条适用于任何 Docker 部署的检查，不只是本项目。**

## 二、三个真问题，一条流全给暴露出来

### 问题 1：探测 15 秒超时 —— 一开始诊断错了方向

GUI 报「探测超时，地址可能已过期」。我先按这个提示去查地址，方向是错的。

同一地址四处对比：

| 环境 | 结果 |
|---|---|
| 本机 Windows ffprobe | ✅ 0.3s |
| NAS 宿主机 shell ffprobe | ✅ 0.0s |
| **NAS 容器内 `/api/probe`** | ❌ **15.0s 超时** |
| **容器内换 IPv4 直连** | ✅ **0.13s** |

结论：**容器里解析到 IPv6 优先，而该 CDN 的 IPv6 不通**（`curl -6` → HTTP 000）。
`ffmpeg` / `ffprobe` 不像 `curl` 会自动回退 IPv4，会一直等到超时。

### 问题 2：`-4` 参数根本不存在（连踩两次）

我第一反应是给 ffmpeg 加 `-4` 强制 IPv4。实测：

```
$ ffprobe -4 -version
Failed to set value '-v' for option '4': Option not found

$ ffmpeg -4 -version
[Windows 构建] 同样 Option not found
[NAS 宿主机 8.1.1] 同样 Option not found
```

**两边的 ffmpeg/ffprobe 都没有 `-4`。** 这个参数只存在于某些文档/派生物里。

改法：Python 层用 `getaddrinfo(AF_INET)` 自己解析出 IPv4，替换 URL 主机名。

### 问题 3：替换主机名会导致 403（这是我引入的新 bug）

替换后录制立刻失败：

```
HTTP error 403 Forbidden (access denied)
Error opening input file http://125.88.186.17/trtc_...
```

两个原因叠加：

1. **视频号 CDN 校验 Host 头**，换成 IP 拉流必然 403
2. **本机 DNS 被抓流工具 MITM**，`getaddrinfo` 返回 `127.208.0.126` 这种假地址

最终处理：

```python
# 录制端：不再替换主机名
self._effective_url = self.url

# 探测端：降级保留，但只接受公网地址
for info in infos:
    addr = ipaddress.ip_address(info[4][0])
    if addr.is_global and not addr.is_multicast:
        ip = info[4][0]
        break
```

## 三、真正的根因：容器 ffmpeg 解不了这条流的视频编码

探测修好后，任务能建、`status=recording`、没有 error —— 但：

```
audio_bytes = 0
```

ffmpeg 日志只有一句不断重复：

```
[flv @ ...] Video codec (c) is not implemented.
```

`(c)` 是**未识别的 4CC 码**。这不是版本旧的问题 —— 实测对比：

| ffmpeg | 结果 |
|---|---|
| 容器自带 **5.1.9**（Debian 12 bookworm） | ❌ 0 字节 |
| 容器装 **7.1.5**（Debian 13 trixie） | ❌ **一样失败** |
| 宿主机 **8.1.1-mediasrv** | ✅ 320KB / 10s |

"升级 ffmpeg 版本"这条常规路**走不通**。fnOS 那个是定制构建：

```
--enable-decoder=hevc_vulkan_shader
--enable-hwaccel=hevc_vulkan_shader
--mediasrv-edition=Mainland
```

### 解决方式：bind mount 宿主机 ffmpeg

```yaml
volumes:
  - /usr/trim/lib/mediasrv:/host-ffmpeg:ro
environment:
  - WXLIVE_FFMPEG=/host-ffmpeg/ffmpeg
  - LD_LIBRARY_PATH=/host-ffmpeg/lib
```

必须挂**整个目录**：它依赖 106 个 `.so`，单拷二进制会缺 `libavdevice.so.62`（实测报错）。
glibc 兼容性验证：容器 **2.41** ≥ 宿主机 **2.36**，符号兼容。

代码侧给 `find_ffmpeg()` 加了环境变量优先：

```python
env = os.environ.get("WXLIVE_FFMPEG", "").strip()
if env and Path(env).exists():
    return env
```

理由：镜像里的 `/usr/bin/ffmpeg` 在 PATH 里必然排前面，光靠 PATH 顺序不够可靠。

## 四、第四个问题：NAS 直连外网全断

这是前面反复失败的隐藏原因 —— 下载静态 ffmpeg 三次都被截断：

```
1.2 MB / 4.2 MB / 2.5 MB   ← 目标 ~25MB
xz: Unexpected end of input
```

测基线：

```
https://www.google.com   000  6.0s 超时
https://github.com       000  6.0s 超时
```

### 解决过程

NAS 上有 v2rayA 的残留配置（`/etc/v2raya/config.json`，VLESS+REALITY 节点），但内核已不在。

- 先用残留配置起 v2ray 容器 → `failed to read response version > EOF`
- 换用订阅的 33 个 VLESS+WS+TLS 节点 → 逐个测 TCP 可达性：**12/33**
- 再逐节点实拉 `google.com`：只有 CZ 节点真的通

最终 `v2ray-proxy` 容器（`--restart unless-stopped`）：

```
宿主机 → 127.0.0.1:20171  (HTTP)
       → 127.0.0.1:20170  (SOCKS5)
```

验证：google / github / johnvansickle 全部 200。

## 六、方法论沉淀

### 1. 「状态字段正常」不等于「功能正常」

`status=recording` + `error=''` + 文件存在，三者同时为真，**产物却是 0 字节**。

本轮踩过两次同类：

- 探测返回 `ok=false` 但错误原因是 IPv6 网络问题，不是地址过期
- 录制返回 `recording` 但 ffmpeg 一个字节都没写

**判据必须是可量化的产物指标**：`audio_bytes > 0` 且**持续增长**，
或者 `|音频时长 - 转写末句时间|` 这类完整性差值。状态字段只说明流程走到了哪一步。

### 2. 报错文案会误导排查方向

原提示：`"探测超时（15s），地址可能无效或网络不通"` + `"地址可能已过期，回微信重新打开"`

这句话让我先去查地址，而真因是容器网络。已改为并列两种可能：

```
探测超时（15s）。两种可能：
· 主播已下播，或地址签名过期
· NAS 到该 CDN 的网络不通（IPv6 黑洞 / 出口被限）
```

**教训：错误文案里写"最可能的原因"时，如果那个原因不一定成立，就会把人带偏。**

### 3. 「升级版本」不是万能解

遇到编码不支持，第一反应是升级 ffmpeg。实测 5.1.9 → 7.1.5 完全无效。

定制的构建参数（`--enable-decoder=hevc_vulkan_shader`）才是差异所在。
**在换版本之前，先确认两个版本的实际能力差异，而不是假设新版一定覆盖旧版。**

### 4. 整个目录一起挂，不要只拷二进制

宿主机的 ffmpeg 只有 423KB，看起来像静态链接。实际 `ldd` 出来 83 个依赖，
`libavcodec.so.62` 单独就有 20MB。

```
只拷二进制 → error while loading shared libraries: libavdevice.so.62
整个目录挂 → 直接可跑
```

### 5. 存量配置会覆盖你改的默认值

这一轮之前就踩过：`retention_days` 默认改 0，但 NAS 上 `settings.json` 里还是 30。
**破坏性默认值变更必须主动迁移存量配置，改代码默认值不够。**
