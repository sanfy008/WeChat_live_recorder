## P0-1 实时录制的产物写错了目录（已复现）

### 现状

`wxlive/pipeline.py:131` 把 `RECORDINGS_DIR` 传给了 `Session`：

```python
self.session = Session(RECORDINGS_DIR, name=cfg.session_name, ...)
# 逐字稿放单独目录（软链/复制关系在 close 时处理）
self._transcripts_dir = TRANSCRIPTS_DIR      # ← 赋值后全文件再未被使用
```

而其余三个入口都传 `TRANSCRIPTS_DIR`：
- `cli.py:356`（离线转写）✅
- `gui.py:921`（离线转写）✅
- `auto_pipeline.py:123`（守护脚本）✅

### 复现结果

```
Session base_dir = recordings
  jsonl_path = recordings / 20261117_163910_demo.jsonl
  md_path    = recordings / 20261117_163910_demo.md
  audio_path = recordings / 20261117_163910_demo.wav
```

### 两个连带后果

1. **产物污染 recordings 目录**。这就是 `output/recordings/` 里混着 6 个
   `.json/.jsonl/.md` 的直接原因（`20261116_104814_live_h2.*`、
   `20261116_105213_final.*`）——那些正是早期"录制+转写"模式留下的。
2. **GUI 打开逐字稿会失败**。`gui.py:819`：

   ```python
   self.last_output = Path(TRANSCRIPTS_DIR) / f"{p.session.id}.md"
   ```

   而 pipeline 实际把 md 写到了 `RECORDINGS_DIR`。
   实测该路径 `exists() == False` → 点"打开逐字稿"打不开。

### 影响面

只影响 **GUI 的「录制 + 实时转写」模式**（`_run_live` → `Pipeline`）。
纯录音模式（`_run_plain`）、离线转写（`transcribe`）都正常。

### 注释与实现不符

注释说"软链/复制关系在 close 时处理"，但 `close()` 里**没有任何迁移逻辑**，
`_transcripts_dir` 是一个纯粹的死变量。
→ 这是「注释描述了意图，代码没实现」的典型，比没有注释更危险。

## P0-2 收尾阶段静默丢音频（代码逻辑确认，未在真实录制中复现）

`pipeline.py` 里同一个操作有两种处理：

| 位置 | 场景 | 队列满时行为 |
|---|---|---|
| 第 218-221 行 | 主循环 | `print("[warn] 转写队列已满，丢弃片段（ASR 跟不上）")` ✅ |
| 第 254-257 行 | **收尾** drain 补写 | `pass` ❌ |
| 第 262-265 行 | **收尾** resampler.flush() | `pass` ❌ |
| 第 269-272 行 | **收尾** segmenter.flush() | `pass` ❌ |

**收尾阶段丢的是整场最后的音频** —— 恰恰是最可能包含结论的部分。
且三条路径连日志都没有，用户完全不知道丢了。

### 严重度判断

`_asr_queue` 容量 200，收尾时最多塞 3 个片段（drain / flush / tail），
**实际打满的概率很低**。但这是"设计上允许静默丢数据"，
与项目自己"任何时刻崩溃都不丢已转写内容"的设计目标不一致。
修法成本极低（加日志 + 失败时落盘到单独文件），值得做。

## P1-1 看门狗只看"流是否活着"，不看"是否还有声音"

### 代码

```python
if self._stream is not None and not self._stream.is_active():
    self._reconnect()
```

只检测 stream 失效。**如果流活着但一直静音（微信暂停/切走/被独占），
看门狗不会做任何事**，用户只能靠"静音 40 秒自动停止"这个功能兜底。

### 今日真实数据佐证

对今天两段录音做静音段分析（1 秒粒度，阈值 RMS<0.005）：

| 文件 | 时长 | >3s 静音段 | 尾部 RMS |
|---|---|---|---|
| `20261117_080255_rec` | 53.2min | **3154s 起连续 39s** | 0.0 ×5 |
| `20261117_090116_rec` | 86.1min | 5064s(3s) / 5107s(14s) / **5123s 起 40s** | 0.0 ×5 |

两段都是「**约 40 秒静音 → 文件结束**」，与「静音 40 秒自动停止」的默认值吻合。
所以这个功能**确实在工作**（第一段录到无人说话就自动停了），
但停下之后需要人工再开第二段。

### 未验证的推测（明确标注）

今天"中间中断"的**具体原因**我没有证据确定：
- 可能是静音自动停止（数据吻合）
- 也可能是微信那边暂停/切换了音频设备
- 或 UU 虚拟声卡端点被切走

**要定性必须下次录制时加日志**（记录每次 stop 的原因码），
而不是靠事后猜。这一点我如实说明，不编造。
