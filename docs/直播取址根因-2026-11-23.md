# 直播列表不显示 / 无法推 NAS 的根因（2026-11-23 实测）

## 现象（King 报）
1. 点「体检」通过。
2. 「刷新列表」看不到正在直播的项 → 不能推给 NAS 录制。
3. 微信里正在直播的内容右上角有下载项，点它会真下本地视频。

## 结论：三个独立缺陷，全部实测复现

### 缺陷 1：直播项被静默丢弃（列表不显示）
`wxlive/fetch.py::_parse_item` 只认 `it["url"]`：

```python
url = str(it.get("url") or "").strip()
if not cid or not url:
    return None      # ← 直播项 url 恒为空，整条丢弃
```

实测 `/api/content/list` 返回 6 条（total=6），其中 2 条 `type=live`
的 `url` 与 `source_url` **都是空字符串**（视频号直播没有静态直链），
于是被 `_parse_item` 丢掉 → 界面只剩 4 条 video，直播一条都看不到。
（`docs` 里 2026-11-17 那版代码就已经这样，不是新引入的。）

### 缺陷 2：直播地址其实一直都在，只是没人去取
直播流地址存在于两个地方，与「点不点下载按钮」无关：

| 来源 | 是否需要先点工具的下载按钮 | 实测 |
|---|---|---|
| `GET /api/content/detail?id=<cid>` → `data.resources[0].url`（= `stream_url`） | **需要**（未点过下载的直播不入库，detail 返回 `content not found`） | 已验证能拉流 |
| `GET /api/logs` 的 `feed.live.liveSdkInfo.liveCdnUrl` | **不需要** | 已验证能拉流 |

实测日志里 7 条不同的 `liveCdnUrl`，**最早一条在 14:07，早于任何下载点击**；
用 `ffprobe` 直接拉最新那条（14:20 `orig_2079009794242106815`）→
`rc=0`，拿到 `aac` + `hevc`，**地址完全可用**。
也就是说用户在微信里打开直播间的那一刻，地址就已经拿到手了。

### 缺陷 3：点下载按钮 = 让工具自己录，与我们无关
工具（wxcd v261106）的直播下载走 `StreamDriver.RecordStream`
（`pkg/hermes/protocol/stream.go`）：它起自己的 ffmpeg 写
`<output>_<uniq>.recording/segment-*.mkv`，失败时重试 3 次。
本机这两条直播任务全部 `status=6` 失败，`error_message`：

```
live recording failed after 3 attempts:
failed to read stream playback directory:
open D:\...\2079009824565503324_1795409177.recording\playback:
The system cannot find the file specified
```

→ 子目录 `playback` 不存在（`stream_playback_start_number` 里 `os.ReadDir` 直接失败）。
**这跟我们的代码无关，也修不了**（第三方二进制）。
而且它即使成功，也是把 400MB 视频下到本地再转 MP3 —— 对「只要音频」是纯浪费。

## 所以「点下载后自动解析」这个思路要改成
不是「点下载 → 我们拦截」，而是：**根本不点下载**。
- 列表里补一条「直播中」的取址路径：`detail.resources[].url`（已入库的）
- 或从 `/api/logs` 抓 `liveCdnUrl`（连点都不用点）
- 「推给 NAS」直接拿这条地址开录，本机可以关

## 附带发现：NAS 侧看门狗没有生效（Critical）
NAS 上 `20261123_141013_114ec5` 从 14:10 起 `recording`，
日志连续 18 分钟刷「文件已停止增长…等待看门狗收尾」，**始终没收尾**。
`wxlive/stream_capture.py::_monitor` 的 90s×3 判据只在
`stale > 90` 时检查，而 `nas_runner._watch_recorder` 每轮
`read_tail_window` 失败走的是 `elif verdict.reason.startswith("文件未增长")`
分支 —— 那条分支**只记日志、不判停**，于是外层循环永远等 `rec.running`。
这正是 MEMORY 里 H1「注释里写了不存在的看门狗保证」的同一处，
上一轮只修了 `_kill_proc`，没修「上层 watcher 也不结束」这一半。
