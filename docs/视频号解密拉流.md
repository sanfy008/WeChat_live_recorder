# 视频号媒体解密与拉流

> 验证时间：2026-11-16 14:58–15:06
> 结论：**整条链路已打通**，实测 94 分钟视频 53 秒拉完（9.9 MB/s）

---

## 一、三个环节，缺一不可

以前以为"拿到流地址就能录"，实测发现中间还有一道加密：

| 环节 | 状态 | 关键点 |
|---|---|---|
| 1. 拿带签名的地址 | ✅ 工具 API 直接给 | `/api/content/list` 的 `url` 字段 |
| 2. **解密** | ✅ 已逆向并实现 | ISAAC64 密钥流 XOR 前 N 字节 |
| 3. 抽音频 | ✅ ffmpeg | 先落盘再处理，不能走管道 |

第 2 步是之前一直失败的原因。

## 二、加密机制

### 2.1 响应头暴露一切

```
X-encflag: 1              ← 1 = 加密了
X-enclen: 131072          ← 前 128KB 是密文
X-snsvideoflag: xWT111    ← 清晰度标记
Content-Type: video/mp4
```

未解密直接喂 ffmpeg 会报：

```
[mov,mp4,m4a @ ...] moov atom not found
Invalid data found when processing input
```

因为 MP4 的 `ftyp` / `moov` 结构正好落在加密区内。

### 2.2 ⚠️ 最大的坑：`X-enclen` 会随 Range 缩水

**这是我在这一轮踩的最深的坑。**

```bash
# 带 Range 请求
curl -H "Range: bytes=0-15" "$URL"
→ X-enclen: 16          ← 只报了你请求的那 16 字节！

# 不带 Range 请求
curl "$URL"
→ X-enclen: 131072      ← 真实加密区
```

用 16 去解密，只有前 16 字节被还原，`moov` 仍在密文里，ffmpeg 依旧报
`moov atom not found`。而我当时误以为"解密成功了"（因为 `ftyp` 确实解出来了），
白折腾了一轮。

**结论：探测 `X-enclen` 必须发不带 Range 的请求。**

### 2.3 解密密钥

藏在内容详情的 `content.metadata` 里：

```bash
GET /api/content/detail?id=wxchannels:14747060388423737247

→ "content": {
     "metadata": "{\"key\":\"8161594\"}"
   }
```

注意 id 必须带 `wxchannels:` 前缀，否则返回 `content not found`。

### 2.4 算法

逆向自 `wx_channels_download`（`pkg/scraper/wxchannels/decrypt.go`）：

```
seed = 密钥（十进制整数）
rng  = ISAAC64(seed)                 ← 标准 ISAAC64 CSPRNG
ks   = 每 8 字节大端拼接 rng.next64()
明文[i] = 密文[i] XOR ks[i]          ← 仅前 enclen 字节
```

只加密头部，之后全是明文——所以下载时只需要对开头一小段做 XOR。

实测验证（key=8161594）：

```
密文前 24: 675cbf11e71c71205a3f5838175d2293e212342faffbd22d
解密前 24: 000000206674797069736f6d00000200e212342faffbd22d
           └ 00000020 长度 │ ftyp isom ┘
```

`ftyp` 出来就说明对了。

## 三、为什么不能走管道

第一次尝试是"边下边解密，管道喂 ffmpeg"，失败：

```
ffmpeg -i pipe:0 → moov atom not found
```

原因：视频号的 MP4 不是 faststart 结构，`moov` 索引在 `mdat` 之后
（实测 `ftyp@4`、`mdat@7326339`）。管道不可 seek，ffmpeg 读到 `mdat`
就以为文件结束，永远等不到 `moov`。

**必须完整落盘，再让 ffmpeg 按文件路径读。** 代价是多占一份临时空间，
但下载只要 50 秒左右，可以接受。

## 四、用法

前提：`tools/wxcd` 的抓流工具在跑（**根命令启动，不要加 `server`**），
且已在微信里打开过目标视频让工具捕获到。

```bash
# 列出已捕获的内容
python -m wxlive fetch --list

# 下载 + 解密 + 抽音频，丢弃视频
python -m wxlive fetch 越秀区 --no-video

# 一步到位：抽完音频直接转写
python -m wxlive fetch 越秀区 --no-video --transcribe
```

参数：

| 参数 | 作用 |
|---|---|
| `target` | 标题关键词或内容 id（模糊匹配标题） |
| `--list` | 列出已捕获内容 |
| `--api` | 工具 API 地址，默认 `http://127.0.0.1:2022` |
| `--name` | 输出文件名，默认用视频标题 |
| `--no-video` | 只留音频，下完删掉视频 |
| `--transcribe` | 接着转写，可用 `--engine` 等参数 |

实测输出：

```
目标：《越秀区各个业主怎么进》
id  ：14747060388423737247
加密：flag=1 enc_len=131072  key=已取到
下载中…
  ...
  429.0 MB    9.9 MB/s
已删除临时视频，保留音频：越秀区各个业主怎么进.wav
时长：93.9 分钟，含音轨：True
```

**94 分钟视频，53 秒完成**，产出 180MB 的 16k 单声道 WAV。

## 五、这样做的好处

对比工具自带的下载：

| | 工具下载 | `wxlive fetch` |
|---|---|---|
| 产出 | 400MB 视频 + 自动转 150MB MP3 | 只要 180MB WAV |
| 转码 | 强制跑 ffmpeg 转 MP3，几分钟 | 无 |
| 磁盘峰值 | 视频 + MP3 两份 | 视频临时 + WAV |
| 能否直接转写 | 要再手动抽音频 | `--transcribe` 直接接上 |
| 耗时 | 下载 + 转码 | 下载即完成 |

工具转 MP3 是写死在流程节点里的（`convert_mp3_node`），配置里没有开关。
所以宁可绕开它自己拉。

## 六、代码结构

```
wxlive/sphdecrypt.py     纯算法 + 流式解密（无业务依赖，可单独复用）
  ├─ Isaac64              ISAAC64 CSPRNG
  ├─ keystream()          生成密钥流
  ├─ decrypt_head()       一次性解密头部
  ├─ DecryptingStream     流式解密（供 urllib 响应包装）
  └─ probe_encryption()   探测 encflag/enclen（注意不带 Range）

wxlive/fetch.py          业务层
  ├─ list_contents()      列出已捕获内容
  ├─ find_content()       按关键词/id 查找
  ├─ get_decrypt_key()    从 content.metadata 取 key
  ├─ download_decrypted() 下载 + 解密 + 落盘
  └─ extract_audio()      抽 16k 单声道 WAV

tests/test_sphdecrypt.py 16 个测试
  ├─ ISAAC64 确定性/取值范围/跨周期
  ├─ 密钥流与 next64 大端拼接一致
  ├─ **真实样本解出 ftyp box**（key=8161594 的固定密文）
  ├─ 只动前 enc_len、尾部原样
  ├─ XOR 幂等（解两次还原）
  └─ 流式分块在各种块大小下与一次性解密结果一致
```

## 七、仍未解决

- **多清晰度选择**：`content.list` 只给一条 `url`（实测都是 xWT111）。
  工具详情接口有 `detail.variants[]`，理论上可以列全部清晰度并选最高，
  目前没用上。
- **地址时效**：`sign` + `svrnonce` 有时效（`Cache-Control: max-age=2592000`，
  但实际以服务端为准）。过期需重新在微信里打开视频让工具刷新。
- **分片/长直播**：本次只验证了单文件 MP4 回放，未验证超长或多段场景。
