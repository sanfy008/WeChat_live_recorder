## 一、起点：一个必须承认的问题

功能做完、379 个测试通过、端到端验证也跑了，但**所有需求都是 King 自己提出来的**——
静音判停、磁盘清理、转录文件库，没有一条是我通过测试或审查主动发现的。

这本身是个缺陷。所以这一轮补上两件事：

1. 自己先做一轮针对性的怀疑性验证（找自己的 bug）
2. 再调 herdr 做独立对立性审查（找我看不到的 bug）

结果：**自己找出 6 个，herdr 再找出 3 个 Critical + 5 个 High/Medium。**

## 二、我自己先找出来的 6 个（全部实测复现）

| # | 问题 | 严重度 | 实测证据 |
|---|---|---|---|
| 1 | **静音重复计数** | Critical | 读 4 秒窗口但只推进 3 秒，重叠 1 秒算两次。真实静音 33 秒被判成 **43 秒**（虚高 30%），提前 10 秒收工 |
| 2 | **文件冻结虚增** | Critical | ffmpeg 卡住不写文件时，每次读同一段旧音频反复计入。真实静音 45 秒能累加到 100+ 秒，判停时机取决于轮询次数 |
| 3 | **WAV 头解析错误** | High | `width` 按「位」读没换成「字节」→ `read_tail` 恒返回空。且标准库 `wave` 在头部 `nframes=0` 时 `setpos` 直接失败（实测 256KB 数据一个字节都读不出来） |
| 4 | **上传窗口误删** | Critical | 上传是"先落盘、后登记任务"，中间窗口内文件会被当孤儿删掉（数据丢失） |
| 5 | **stop_reason 丢失** | Medium | 静音停止原因 `persist=False` 只写内存，重启即丢，无法事后归因 |
| 6 | **清理日志句柄泄漏** | Medium | `open().write()` 不关文件，7x24 常驻累积；日志还无限增长 |

### 关键方法：修复后必须重新量化

第 1 项修复后我重新跑同一场景：

```
修复前: 真实静音 33s → 计数器 43s (误差 +10s / +30%)
修复后: 真实静音 42s → 计数器 42s (误差 +0.0s)
```

**"改完觉得对了"不算数，必须拿同一组数字对比。** 这和 MEMORY.md 里
「验证链路前先量化噪声」是同一条原则。

## 三、herdr 独立审查找出的问题

审查耗时 5 分 38 秒，输出分 Critical/High/Medium/Low 四级，
每条标了「已复现」还是「推断」。这是它的价值——**我的自查找不到 C1 这类跨模块链式问题。**

### C1：jobs.json 单条畸形 → 全量误删（最严重）

```
旧代码: for j in raw.values(): j.get("status")   ← 一条不是 dict 就 AttributeError
        except Exception: return {}             ← 整份任务表变空
```

链式后果：
1. `referenced_audio` 清空 → 所有老音频被当"孤儿"
2. 下次 `_save_jobs` 把空表**写回磁盘** → 原始记录永久消失
3. 启动 60 秒后清理线程真删，**全程无人工确认**

我实测复现了：

```
输入: {"j1": {正常任务}, "j2": "oops"}
结果: 加载后 jobs = 0 条 → 健康任务的 100 天前录音被列入待删清单
```

**这条能在一夜之间毁掉全部历史录音。** 修法三重：

1. 逐条容错（坏条目跳过并备份到 `jobs.corrupt.json`）
2. 真删前二次保护：有损坏、或"任务表为空但目录里有音频"→ 拒绝执行
3. 预览时给出 warning，让人知道真删会被拒

### C2：默认开启删除 + 不可审计

原设计默认 30 天自动删。审查指出：新装即生效、第 31 天自动删、不可撤销、
无回收站、日志只记"删了几项多少 MB"不记删了什么。

修法：
- 默认改成 `retention_days=0`（必须显式开启）
- 每次删除把**完整路径清单**写进 `cleanup_history/`（保留最近 100 批）

### C3：破坏性端点无鉴权

`serve` 默认绑 `0.0.0.0`，`/api/cleanup/run` 能直接删数据。
局域网任何主机都能调，恶意网页可借 DNS rebinding 绕过同源。

修法：可选 token + Host 头白名单。容器内实测：
```
evil.example.com → 400
127.0.0.1 / localhost → 200
```

| H1 | 卡死 ffmpeg 永不收尾：`_monitor` 断流后只 break 不杀进程，`running` 仍 True → watcher 永远循环 | **最认同这条**。而且我自己的代码注释里写着"看门狗会接手"——那句话是错的 |

## 四、两个我判断错了的地方

### 1. 我以为"看门狗会接手"，实际不会

`nas_runner.py` 里我写过这样的注释：

> 若同时 CDN 已断流，StreamRecorder 的 90s×3 看门狗会接手收尾

审查发现 `_monitor` 连续断流后**只 `break` 退出自己的线程**，不 kill 进程。
`running` 属性看的是 `proc.poll() is None`，进程活着就还是 True →
上层 watcher 永远等下去。

**我在注释里写了一个不存在的保证。** 这比没有注释更危险。

### 2. C2 修默认值不够，存量用户仍会静默删

改完 `retention_days` 默认 0 后部署到 NAS，发现实际还是 30——
因为 **NAS 上已有 `settings.json` 里的旧值会覆盖新默认值**。

这不是代码 bug，是**迁移问题**：改默认值只对全新安装生效。
已把 NAS 上的值改回 0，等你确认后再开。

**教训：改默认值要考虑存量配置。** 破坏性默认值变更应该主动帮用户迁移，
而不是指望"新默认值会自动生效"。

## 六、方法论：这轮沉淀的三条

### 1. 「测试全绿」不等于「没问题」

379 个测试全过的时候，里面藏着 2 个 Critical。
因为测试写的是**我想到的场景**，而 bug 在我没想到的地方。

所以：功能做完后必须再做一轮"假设这里有 bug"的验证，
而不是拿"测试通过"当收工信号。

### 2. 自己审查和外部审查找的是不同类别的问题

| | 我自查找出的 | herdr 找出的 |
|---|---|---|
| 类型 | 单模块内的算法错误（重复计数、解析错位） | 跨模块链式后果（损坏→误删→覆盖→真删） |
| 原因 | 我能看到自己写的代码细节 | 它能跳出我的实现思路看系统行为 |

**两类都要有。** 只有自查会漏系统性问题，只有外部审查会漏实现细节。

### 3. 破坏性功能的默认值必须是"不做事"

清理、删除、覆盖这类操作，默认值应该是**关**。
"新装即生效"对只读功能是便利，对破坏性功能是陷阱。

配套：任何自动决策的删除，必须留下**可追溯的清单**（删了什么、什么时候、为什么）。
