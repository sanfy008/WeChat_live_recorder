# 视频号下载页 GUI 改进调研

调研时间：2026-11-16 · 检索源：GitHub Search API + 逐个读源码/README
起点问题：现有「视频号下载」页功能不全 —— 缺删除/清空列表、缺"是否解析"的提示。

---

## 一、结论先行

| 诉求 | 能否做 | 怎么做 |
|---|---|---|
| 删除选中条目 | ✅ 但只能本侧隐藏 | 工具无删除 API，见第二节 |
| 清空列表 | ✅ 同上（另有"只清下载标记"语义） | `fetch_state.json` 的 `hidden` |
| 恢复被删除的 | ✅ | 一键清空 `hidden` |
| 是否获取解析（提示） | ✅ | HEAD 探测：地址死活 / 是否加密 / 文件大小 |
| 搜索 / 翻页 | ✅ | 工具的 `keyword` + `limit`/`offset` 本来就支持，之前没用 |

**一句话**：抓流工具能给的比我们用的多得多（服务端搜索、总数、分页、作者、
发布时间），但它**没有删除能力**，所以"删除"只能是视图层的事。

---

## 二、硬约束：抓流工具没有删除 API

用的工具是 [ltaoo/wx_channels_download](https://github.com/ltaoo/wx_channels_download)
（`tools/wxcd/wx_video_download.exe`）。我把它的 `internal/api/routes.go`
全量路由拉下来核对过：

```
GET  /api/content/list        ← 我们在用（支持 keyword/limit/offset/page/page_size）
GET  /api/content/detail      ← 我们在用（取 metadata.key）
GET  /api/content/relations
```

**没有 delete / clear / remove / clean 任何一条**。我实测过
`POST /api/content/delete`、`/api/content/remove`、`/api/v1/content/delete`
全部 404。

它自己的数据库是 `tools/wxcd/data.db`（SQLite，WAL 模式，运行中）。
直接去写它的库风险太大 —— WAL 边写边改极易写坏，工具里攒的捕获记录会全丢，
而这些记录是"重新拿到流地址"的唯一凭据（地址带签名有时效，过期就得靠记录里的
source_url 回去重开）。

**所以**：删除/清空 = 记进我们自己的 `config/fetch_state.json`，刷新时过滤。
界面上必须写清楚"只影响本工具列表，不动物具数据"，并给"恢复"出口。

### 顺带纠正一个认知

工具**不是**只能给一条 url。它的 `/api/content/list` 返回的每条都带：

| 字段 | 用途 | 之前用了吗 |
|---|---|---|
| `accounts[].nickname` | 作者名 | ❌ 现在加了 |
| `publish_time` | 作品发布时间 | ❌ 现在加了 |
| `created_at` | 被捕获的时刻 | ❌ 现在加了 |
| `total` | 总数（翻页必需） | ❌ 现在加了 |
| `keyword` 查询参数 | **服务端** LIKE 搜索 | ❌ 现在加了 |
| `limit` / `offset` | 分页 | ❌ 现在加了 |

之前的实现只取了 `external_id` / `title` / `url` 三个字段，
所以"共几条""能不能搜""翻页"全都没法做 —— 不是工具不支持，是没接上。

## 三、可借鉴的同类项目

### 1. [gui8912/wxchannels-downloader](https://github.com/gui8912/wxchannels-downloader) ★1

星少但**设计密度最高**，README 有 433 行，几乎每个功能都写了"为什么"。
同类里最值得抄的一份：

| 它的做法 | 我们抄了什么 |
|---|---|
| 按「**标题 + 文件大小**」认人去重 | 记进 README：回放每请求一次就换一套 `svrnonce`，`url` 和 `decode_key` 每次都不同，**按 URL 去重等于没去重** |
| 只留"正在播放的那条" | 暂未做（判据是播放进度上报，要 MITM 注入钩子，成本高） |
| 「🩺 体检」把缺项直接列出来 | ✅ 加了「体检」按钮，读 `/api/status` 显示版本/API/代理状态 |
| 把 HTTP 错误翻译成可执行建议 | ✅ 解析失败时说"地址可能已过期，请在微信里重新打开该视频"，而不是抛 `403 Forbidden` |
| 任务队列串行 + 全部暂停/恢复 + 持久化 | 部分抄：串行 + 可中止（`_fetch_cancel`）；队列持久化暂未做 |
| 嗅探列表"只认真的点过播放的" | 未做（同上，需注入） |
| 静音 N 分钟自动停 | 未做（我们不做录制，只做下载） |

它的 v5.7.7 版本记录尤其有价值 —— 一整节在讲"嗅探列表为什么堆垃圾"，
三个原因（同一路流重复入列 / 昨天的记录被重放 / 房间里报上来一堆直播间）
全都是**时间戳缺失**导致的。这类"看起来是 UI 问题、实际是数据没记全"的
经验，正是我们这次补 `captured_at` 的动机。

### 2. [qiye45/wechatVideoDownload](https://github.com/qiye45/wechatVideoDownload) ★6.0k

最主流的那个（6k 星）。功能清单直接就是需求清单：

- **清空列表** ← 用户提的就是这个
- 标题显示可选（有的标题是乱码/空，不显示更好）
- 下载进度条
- 直播分段时间可设更长
- 修复"同名视频被覆盖" ← 我们也踩到了，见下
- 微信 4.0 支持

「同名视频被覆盖」这条我直接采纳了：`fetch.unique_path()`
会给同名文件追加 `(2)(3)…`。同一个主播开两场，标题经常一模一样。

### 3. [knowing-top/ChannelsDownloader](https://github.com/knowing-top/ChannelsDownloader) ★28

Electron + React + antd + xstate，架构最"正规"。

它的 UI 设计值得抄的是**状态切换**：
一旦这条已经下过，按钮从「解密下载」变成「查看」（直接 `shell.openPath`）。
我们这个版本换成了状态列显示「已下载 N 分钟」，效果一样但更省地方。

它的 xstate 有限状态机（检测初始化 → 初始化完成 → 下载中）思路不错，
但 tkinter 里上状态机是过度设计，我们用 `_fetch_busy` 布尔 + 按钮灰化就够了。

## 四、我们实际做了什么

### 列表能力（补全工具已有的能力）

- **搜索**：交给服务端（`keyword`），输入停 400ms 防抖。
  实测中文必须 URL 编码，不编码服务端收到乱码返回 0 条。
- **翻页**：`limit` / `offset`，显示「第 1 / 3 页」，首页/末页按钮自动灰掉。
- **每页条数**：20 / 50 / 100 / 200 可选（默认 100）。
  不能太大：每条都带一个约 1000 字符的签名 URL，500 条就是 500KB 响应。
- **列**：标题 / 作者 / 发布时间 / 状态。
- **Ctrl+A 全选**（Treeview 默认不支持）、反选、双击解析。

### 删除 / 清空 / 恢复（本侧视图）

| 操作 | 行为 |
|---|---|
| 删除选中 | 写进 `hidden`，刷新后不显示。确认框明确写"不动物具数据、可恢复" |
| 清空列表 | 三选一：隐藏全部 / 只清"已下载"标记 / 取消 |
| 恢复被删除的 | 一键清空 `hidden` |
| 显示已删除的 | 勾选后隐藏条目以灰色重新出现，状态列写「已删除（隐藏）」 |

细节：如果在"显示已删除"视图里选中了隐藏条目再点删除，
会自动转成"要不要恢复"—— 否则语义会拧成"删除一个已删除的东西"。

### 是否获取解析（用户提的"是否获取解析的提示"）

理解成两种需求，都做了：

**A. 下载前先解析（开关，默认开）**
下载前对每条做一次 `HEAD`：

- 地址还活着吗（401/403 → "可能已过期，请在微信里重新打开该视频"；404 → 已下架）
- 要不要解密（`X-encflag` / `X-enclen`）
- 多大（`Content-Length`，能显示"621.2 MB"而不是只给脉冲动画）

代价是一个 HEAD 请求（实测几十毫秒）。收益是：地址过期时**立刻**知道，
而不是下到 0 字节才发现；顺带能提前判断要不要取解密密钥。

**B. 「解析选中」按钮（手动）**
把结论写进状态列和日志，例如「可下载 加密 / 621.2 MB」。
失败会累积到一条总结："N 条解析失败，地址有时效，需回微信重开"。

### 其他

- **同名文件避让**：`unique_path()` 追加 `(2)(3)…`，
  视频和 WAV 都避让（之前 WAV 会覆盖上一场的音频）。
- **已下载记账**：`fetch_state.json` 的 `downloaded`，记路径/时长/大小，
  下次刷新这条显示「已下载 10 分钟」。「只看未下载的」据此过滤。
- **中止**：`threading.Event` 置位，worker 在循环里检查。
  不硬杀线程（会把 `.part` 留成半截）。已下完的那条仍会转出音频再停，不浪费。
- **体检**：读 `/api/status`，显示工具版本 / API / 代理状态。
- **空结果给解释**：如果读到 N 条但全被视图过滤掉，弹窗说明是哪个开关挡的 ——
  不能只给一个空列表让人以为坏了。

## 五、踩到的坑

### 1. `probe_encryption` 的 Range 头陷阱（已有注释，这次抽成 `head_info`）

带 `Range: bytes=0-15` 请求时，服务端返回的 `X-enclen` 会跟着缩成 16，
而真实加密区是 131072。用缩水值解密只还原前 16 字节，`moov` 仍在密文里，
ffmpeg 照报 `moov atom not found`。

这次把响应头解析抽成 `head_info()`，`probe_encryption` 改成委托它 ——
避免两处各写一遍、一边带 Range 一边不带。

### 2. Tk `Treeview` 的行 iid 不是业务 id

行 iid 是 Tk 自己生成的 `I001`/`I002`，跟 `content_id` 无关。
状态回写必须靠「行内容 → cid」反查。反查键用
`(title, author, publish)` 三元组，不是单独的 title ——
同一个作者同名标题真的存在（同一场直播分两段）。

### 3. 测试会打到真实工具

老测试用 `monkeypatch.setattr(F, "list_contents", fake)` 打桩，
但新实现走的是 `list_page`，桩没打到 → 请求真的发到 `127.0.0.1:2022`，
拿到真实数据，测试变成看运气（还读到 4 条真实数据，断言全错）。

修正：所有用例显式替换 `list_page`，并且把 `fetchstate.STATE_PATH`
指到 `tmp_path`，避免测试污染真实的隐藏列表。

## 六、有意不做的

| 项 | 为什么 |
|---|---|
| 多清晰度选择 | 工具 `content.list` 只给一条 url（实测都是 `xWT111`）；详情接口的 `assets[]` 也是单条。要做得多打一次 detail 并解析 `assets`，收益小 |
| 「只留正在播放的」过滤 | 判据是播放进度上报（`pc_findergetbulletcomment` 的 `object_id`），需要 MITM 注入 JSBridge 钩子。成本远高于收益 |
| 任务队列持久化 | 我们不做长时间挂机录制，下载是一次性动作，重启后重选即可 |
| 去碰工具自己的 `data.db` | WAL 模式 + 运行中，写坏会丢全部捕获记录；而记录是"地址过期后重新取址"的唯一凭据 |

## 八、系统代理被接管后不还原的问题（2026-11-16 追加）

### 现象

用户在微信里抓流下载时，抓流工具会把**系统代理**改成 `127.0.0.1:2023`
（它自己的 MITM 端口）。工具一关，2023 没人监听，但**系统代理还指着它** ——
所有走系统代理的应用（浏览器、微信、系统更新、部分桌面客户端）全部断网。

实测（2026-11-16 16:12）：代理指向未监听端口时 `curl` 报 `000` 并卡满超时。
这是"突然上不了网"最常见的原因，而且用户几乎不会想到去查代理。

### 纠正一个容易记错的细节

用户记忆里是"下载完要恢复为 10808" —— 方向对，但**机制不是"下载完恢复"**，
而是"**工具退出时恢复**"。而且不一定恢复得回来：

| 退出方式 | 会不会还原 |
|---|---|
| Ctrl+C / 正常关窗口 | 会（工具有 defer 还原逻辑） |
| 任务管理器结束进程 | ❌ 不会 |
| 工具崩溃 | ❌ 不会 |
| 电脑没关工具就休眠/重启 | ❌ 不会（注册表是持久的） |

更麻烦的是：即使工具还活着，**只要它一退出就是全网断**，而用户往往
已经切去做别的事了。所以"靠工具自己还原"不能作为唯一保障。

### 已确认的当前状态（2026-11-16 16:12 实测）

```
ProxyEnable = 1
ProxyServer = 127.0.0.1:2023        ← 工具接管中
proxy.upstreamproxy = http://127.0.0.1:10808   ← 工具转发到固定出口
HTTP_PROXY / HTTPS_PROXY = http://127.0.0.1:10808  ← 进程级不受影响
```

也就是**现在就是风险状态**。只是因为 wxcd 恰好还在跑（PID 25684 监听 2022/2023），
才没断网。

### 为什么不能只靠"备份还原"

之前留过 `tools/proxy-backup.txt`（`1|127.0.0.1:10808`）和
`tools/proxy-backup-1424.txt`（完整三字段）。快照方案有两个问题：

1. **备份可能本身就是坏的**：如果备份时工具正在接管，存下来的就是 2023
2. **多次进出后失真**：抓流 → 还原 → 再抓流 → 再备份，容易备份成中间态

所以本项目的还原**不读快照，直接写已知的固定值** `127.0.0.1:10808`
（MEMORY.md 记录：本机固定出口长期不变）。

### 做了什么

新增 `wxlive/systemproxy.py`：

| 函数 | 用途 |
|---|---|
| `read()` | 读 ProxyEnable / ProxyServer / ProxyOverride |
| `describe()` | 一行状态描述，带"工具接管中"的警告 |
| `diagnose()` | 体检用：该不该动手，`⚠` 开头表示已经在断网 |
| `is_tool_takeover()` | 是否指向 2023 |
| `is_fixed_proxy()` | 是否已是 10808 |
| `restore_fixed()` | 写回 10808 并通知 WinINET 刷新 |
| `tool_still_running()` | TCP 连一下 2023，判断工具死活（不依赖进程名） |
| `refresh_wininet()` | `InternetSetOption` 通知系统，让已开着的浏览器立刻感知 |

GUI 下载页顶部新增**常驻状态条**：

- 启动就读一次，之后**每 60 秒自检**
- 正常显示灰色；抓流工具已死但代理还指着 2023 时变橙色 + 写日志
- 右侧「还原系统代理」按钮，一键写回 10808
- 还原前会提示：如果工具还在跑，还原后微信流量不再经过它，会抓不到新内容

### 设计取舍

**不常驻监控、不自动改注册表。** 理由：
- 自动改注册表是系统级副作用，静默做用户不知道发生了什么
- "每 60 秒检查 + 醒目提示 + 一键按钮"已经能在 1 分钟内发现问题

**只在还原时写注册表。** 已经是 10808 时直接报"无需还原"，不重复写。

### 端到端验证

- 真实环境：`describe()` → `系统代理：127.0.0.1:2023（抓流工具接管中，关掉工具会断网）`
- 真实环境：`diagnose()` → `系统代理 127.0.0.1:2023（工具在跑）。用完记得关工具或点「还原系统代理」`
- GUI：状态条正确显示上面那行
- 测试：新增 4 个（已是固定值时不写注册表 / 用户取消不写 / 确认后调用 / 状态显示）
- 全量 **169 个测试通过**

### 顺带修掉的一个测试基础设施问题

加了 60 秒定时自检后，全部 GUI 测试从 20 秒变成"跑不完卡死 250 秒"。
两个原因叠在一起：

1. **`after` 定时器让 Tk 事件循环永远有事可做** → `destroy()` 后进程不退出。
   修法：新增 `fetch_shutdown()` 取消所有 `after`，接进 `_on_close()` 和测试 fixture。
   > 这个 bug 在真实环境里同样成立 —— `pythonw` 关窗口后进程残留。
2. **`messagebox` 是模态的**，测试里没人点就永远等下去。
   修法：fixture 里默认把所有 messagebox 换成 noop，
   需要断言弹窗内容的用例再自己覆盖。

修完：34 个下载页用例从 167 秒降到 **20 秒**。
