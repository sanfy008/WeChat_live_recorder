## 关键发现 1：401 不是"缺功能"，是"旧进程 + 三个隐藏缺陷"

### 表面结论（King 的观察，准确但只是最外层）

> 「解析出来之后发送到 NAS 解析，有错误，需要 token，但是在 GUI 界面没有输入 token 的选项」

日志印证：`07:46:21` 起连续 5 次

```
[NAS] NAS 支持服务端解密，直接推送《深度聊聊广州二中》…
[NAS] 推送失败 HTTP 401：{"detail":"需要有效的 X-WXLIVE-Token 头或 ?token= 参数"}
```

### 真因（时间线证据链，非推断）

| 事实 | 时间 |
|---|---|
| 正在跑的 GUI 进程（PID 1756/6548）启动 | **2026-11-26 17:55:36** |
| 令牌输入框写进代码的提交 `043429f` | **2026-11-27 11:14** |
| NAS 开启 `WXLIVE_TOKEN` 鉴权 | 11-27 13:02 |

**窗口比重码早了 17 小时。**`gui_fetch.py` 里那个「令牌」输入框
从来没被加载过 —— 不是漏了功能，是**屏幕上那个窗口是旧的**。

这直接复现了 MEMORY 里那条老账：「GUI 进程存活多天，跑的是旧代码」。

### 但顺着查下去，还有三个真缺陷

| # | 缺陷 | 为什么危险 |
|---|---|---|
| 1 | 令牌框 `width=12` 且 `show="*"` | NAS 令牌是 **43 位**，粘进去只见几个星号，输错无任何反馈，只收到 401 |
| 2 | 地址/令牌**从不落盘** | 每次开窗口回到硬编码默认值，令牌永远空 |
| 3 | 「体检」只打 `/api/health` | 那是**免令牌**端点，令牌错也显示"在线" → 点了体检全绿，一推送就 401 |

### 关于"自动获取解密 token"这个设想

King 提出「能不能自动获取解密 token」。核实后发现**这里混了两个不同的 token**：

| | 是什么 | 实际状态 |
|---|---|---|
| `decodeKey` 解密密钥 | 加密回放视频的 DRM key | **早已全自动**。从 wxcd 日志 `set_feed` 与 `/api/content/detail` 捞取；日志里每一条「NAS 支持服务端解密，直接推送」都说明它已拿到 |
| `X-WXLIVE-Token` 访问令牌 | NAS 自身鉴权（43 位随机，防公网白嫖） | 才是 401 的原因，**必须人工填一次** |

**结论：`X-WXLIVE-Token` 在原理上不可能"自动获取"** —— 它是 11-27 亲手设在
NAS `.env` 里的密钥，能自动拿到就等于鉴权失效。能自动化的只是
「**存一次、以后免填**」，这一条已落地。

> 方法论：用户描述的是**症状**，不是**范围**。这句话准确描述了最外层，
> 但顺着挖下去是 3 个不同层的问题。只修最外层 = "窗口不消失但仍不能用"，
> 反而更难排查（同 MEMORY「用户描述的是症状不是范围」）。

King 追问「GUI 的版本号是不是一直没变」。核实结果比"没变"更糟：

| 位置 | 原值 | 最后变动 |
|---|---|---|
| 标题栏 `gui.APP_VER` | **1.0** | 2026-11-16 首次提交（`ce9c0e3`）后**再没动过** |
| 包 `__init__.__version__` | 0.2.0 | 11-17 |
| `RESUME.md: project_version` | v0.4.0 | 11-27 |

62 个提交、12 天演进，标题栏还写着 `v1.0`。

### 危害不是"不好看"

真正的问题是**没法回答「屏幕上这个窗口是哪一版」**。
这和本次 401 故障里「分不清新旧进程、把旧版当功能缺失」是**同一类错误**。
所以修法不能只改数字。

### 做法

1. `wxlive/__init__.py` 收口为唯一真相源：`__version__` / `VERSION_LABEL`
2. 删掉 `gui.py` 的硬编码，标题栏变为 `微信直播录音转写 v0.5.0 · 4b20f7`
3. **新增源码指纹** `build_stamp()`：对 `wxlive/*.py` 的 mtime+size 取 6 位短哈希。
   **改了代码但没重启 → 指纹不变**，一眼看出窗口是旧的。
   刻意不依赖 git（用户机器未必有；`pythonw` 下跑 git 会弹黑框）
4. 启动写日志：`启动 … v0.5.0 · 源码指纹 4b20f7 · PID 25768`
5. 新增 `tests/test_version.py`（5 用例）锁住一致性

## 关键发现 3：我自己的改动污染了生产日志

给 App 加「启动写日志」后，测试 fixture 从未隔离 `OUTPUT_DIR`，
于是每次跑 pytest 都往真实的 `output/logs/gui_YYYYMMDD.log` 写一条假「启动」。
跑一轮全量实测塞进 **107 条**，还夹着「设置已保存」。

**这是「产物看起来正常比报错更危险」的变体**：测试全绿，
但它污染了**排查问题所依赖的日志** —— 下次再遇到"跑的是哪一版"就又看不出来了。

修法：fixture 里 monkeypatch `wxlive.gui.OUTPUT_DIR` 到 tmp_path。
**注意坑**：`gui.py` 是 `from .config import OUTPUT_DIR` 直接绑定名字的，
改 `config` 模块无效，必须改 `gui` 模块里的名字。

验证方式：跑测试前后日志行数均为 206，**零增长**。

## 经验沉淀（新增判据）

### 1. 「免鉴权端点」不能用来验证鉴权

`/api/health` 刻意放开令牌（好让网页前端在弹令牌框前知道自己活着）。
拿它当体检 = 令牌错也显示"在线"。

**可复用判据**：要验证鉴权是否通过，必须打一个**需要鉴权的端点**。
本轮做法：发空 body 的 `POST /api/probe` 当探针 ——
`401` = 被鉴权拦住（令牌问题）；`422`/`2xx` = 过了鉴权。
该请求不建任务、不碰磁盘，无副作用。

**更一般地**：绿灯必须来自**与失败同一层**的检查。
用上一层（"机器在线"）的绿灯推断下一层（"鉴权通过"），就是假绿灯。

### 2. 整体覆盖写的配置保存，要检查字段是否会丢

`save_user_config` 是整体覆盖。任何新增配置段若没同步进
`_collect_settings`，点一次「保存」就静默清零。

**可复用判据**：新增配置段时，问一句「另一条保存路径会不会把它抹掉」，
并写测试断言"保存前后值不变"。这类丢失不报错，只在下次使用时暴露。

### 3. 给"运行中产物"加副作用时，先问测试会不会碰到它

加启动日志的当下就该想到「pytest 会创建 App」。
**可复用判据**：任何写文件的副作用，都要检查测试 fixture 是否已隔离对应目录。
本轮验证方式很直接 —— **跑测试前后比对日志行数，应为 0 增长**。

### 4. 前端硬编码的版本号必然过期

**可复用判据**：版本号只允许一处定义，其余全部引用；
并用测试断言"标题栏版本 == 包版本"，以及"源码里不存在硬编码版本字面量"。

### 5. 容器是 COPY 进镜像的，改代码必须 `--build`

本轮第三次踩到：宿主机 `artifacts.py` 是最新的，但容器里没有 `check_segments`，
产物 `meta.quality` 缺失。**`docker restart` 无效，必须 `up -d --build`。**

**三层验收判据**（别用上层绿灯推断下层）：
```
① 宿主机文件 MD5 == 本地        → 只证明"文件到了"
② 容器内 import 新模块成功      → 才证明"镜像里有新代码"
③ 用新函数跑一份真实产物        → 才证明"新代码真能跑通"
```
